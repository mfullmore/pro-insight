Interactive Budget Plans — Implementation Options

Four working implementations of the same idea: turn a department budget spreadsheet into an interactive, editable page that lives where your team already works. This compares them so you can pick a starting point.

All four options do the same core job — parse a budget .xlsx, recalculate its formulas live as someone edits a value, and produce a new version with those edits captured. What differs is how a plan gets created, where it lives, and how much needs to be installed or deployed to get there. None of them require adopting a new platform: each one meets your team inside a tool it likely already uses.

Shared across all four

  • Same conversion engine (SheetJS to parse the workbook, HyperFormula to recalculate it) — the underlying behavior and limitations are identical regardless of which option you pick.
  • Same safety principle: a formula the engine can't evaluate (dynamic INDIRECT() lookups, Excel Table references) is flagged explicitly and shown as an error, never silently replaced with a plausible-looking wrong number.
  • Data never leaves your organization's own platform in any of the four — no third-party server is involved in any option.
  • Same interactive-plan UI everywhere: a sidebar lists sheets (with a flagged-formula count badge per sheet), each sheet renders as a card-based table. Redesigned once inside the shared rendering engine, so no option-specific UI code was needed — it stays fully generic, making no assumptions about sheet names or column meaning, same as the conversion engine itself. The two options with their own separate tool page — the Browser Converter's upload page and the Excel Add-in's task pane — now match the same look too; Confluence and SharePoint have no separate page of their own to match, since the interactive plan is their whole UI.

Each option in brief

Option 1

Browser Converter

A single page you open in any browser. Drop in a budget spreadsheet, get back an interactive page — no account, no install, no approval process of any kind.

Best for: proving the idea fast, or teams without the ability to install anything.
Option 2

Excel Add-in

A button inside Excel itself. Reads the workbook's already-computed values directly from Excel, so the export always starts accurate — no re-derivation risk on the first pass. Sideloaded and confirmed working in Excel for the web against a real budget workbook.

Best for: teams already standardized on Microsoft 365 admin tooling for add-in rollout.
Option 3a

Confluence App

Lives directly on the Confluence page as a macro. Reads whatever budget file is already attached — no upload step — and writes new versions straight back as an attachment. Confirmed working on a live site, including a real version write-back.

Best for: teams whose budgets already live in Confluence, wanting zero extra steps for anyone viewing the page.
Option 3b

SharePoint Web Part

Lives directly on a SharePoint page. Reads a configured file from a document library and writes new versions straight back — the same native experience as the Confluence option, for SharePoint. Confirmed working end to end on a live Microsoft 365 site, including a real version write-back.

Best for: teams whose budgets already live in SharePoint, wanting the same zero-step experience.

A reasonable way to sequence this

These aren't mutually exclusive — the underlying conversion logic is shared, so trying one doesn't commit you to it.

  1. Start with the Browser Converter. It needs no approval from anyone, so it's the fastest way to put a real interactive plan in front of actual budget owners and see whether the core idea lands before investing further.
  2. Once there's buy-in, pick the platform integration that matches how your organization is actually set up — the Excel Add-in if rollout goes through Microsoft 365 admin tooling, the Confluence or SharePoint option if budget pages already live there and the "no separate step for anyone" experience is worth the deployment effort.
  3. The native platform options (3a/3b) are the only two that remove the manual save/re-share step entirely — worth weighing that against their deployment overhead: both required real one-time platform setup (a Confluence Developer Space, a SharePoint tenant App Catalog) before the app could even be installed.
